================================================================================
АЛТАЙ-ВИТРИН — ТЕХНИЧЕСКОЕ ЗАДАНИЕ: БЭКЕНД «ПОЛКИ» (ОНЛАЙН-ВИТРИНА / «ТВОЯ ПОЛКА»)
================================================================================
Документ для передачи в разработку или в промпт ассистенту. Фронт на статике
уже отражает концепт «комнат» и зон полок; этот файл описывает, что нужно
реализовать на сервере.

-------------------------------------------------------------------------------
1. ПРОДУКТОВАЯ МОДЕЛЬ
-------------------------------------------------------------------------------
1.1. Комната (room / category hall)
  — Логический раздел каталога: например «Освещение», «Текстура», «Декор»,
    «Мебель». У каждой комнаты свой набор «полок» и правила отображения.

1.2. Полка (shelf placement)
  — Единица аренды видимости для карточки товара внутри комнаты.
  — Два независимых измерения тарифа (можно покупать раздельно или вместе):
    A) Вертикаль / высота в комнате: верх полки (уровень глаз), середина, низ.
       Чем выше — дороже (аналог полки ближе к глазам в офлайн-магазине).
    B) Ширина слота: сколько мест занимает карточка в ряду (узкая / стандарт /
       широкая). Шире — дороже.

1.3. Комбо
  — Покупка и высоты, и ширины одновременно — отдельный тариф, дороже суммы
    по отдельности (на усмотрение прайсинга).

1.4. Динамические полки
  — Внутри одной зоны (верх/середина/низ) порядок карточек не обязан быть
    строго фиксированным навсегда: допускается пересчёт позиций по правилам
    (ставка, время до конца аренды, перегрузка зоны и т.д.). Нужны явные
    правила ранжирования в коде и в документации для продавцов.

1.5. Срок аренды
  — У каждой активной полки есть дата/время начала и окончания.
  — По истечении срока полка становится неактивной (см. видимость ниже).

-------------------------------------------------------------------------------
2. ВИДИМОСТЬ И РОЛИ
-------------------------------------------------------------------------------
2.1. Обычный посетитель (гость / покупатель)
  — Видит только карточки с активной оплаченной полкой (в пределах срока).
  — Не видит просроченные размещения.

2.2. Владелец товара / продавец (дизайнер)
  — Видит свои товары с истёкшей полкой в личном кабинете (статус «срок истёк»,
    карточка не в публичной витрине).
  — Может продлевать аренду (оплата нового периода).

2.3. Администратор
  — Видит все полки, в т.ч. просроченные, для модерации и поддержки.
  — Доступ к ручному отключению/возврату средств — по бизнес-процессу.

-------------------------------------------------------------------------------
3. УВЕДОМЛЕНИЯ О КОНЦЕ АРЕНДЫ
-------------------------------------------------------------------------------
3.1. За 24 часа до окончания срока аренды полки:
  — Отправить автоматическое письмо на email пользователя, указанный при
    регистрации (аккаунт продавца).
  — Текст: напоминание, дата/время окончания, ссылка на продление, контакт
    поддержки.

3.2. Каналы (минимум):
  — Email (обязательно в первой версии бэкенда).
  — Опционально позже: push, in-app колокольчик.

3.3. Надёжность
  — Очередь задач (cron / scheduler / worker), идемпотентность писем
    (не слать дубликаты), логирование отправок и ошибок.

-------------------------------------------------------------------------------
4. ДАННЫЕ (ЧЕРНОВИК СУЩНОСТЕЙ)
-------------------------------------------------------------------------------
User
  id, email, password_hash, role (buyer | seller | admin), created_at, ...

Room
  id, slug, title, sort_order

ShelfListing (размещение товара на полке)
  id
  product_id
  room_id
  tier ENUM(top | middle | bottom)   — вертикаль в комнате
  width_tier ENUM(narrow | standard | wide)
    — на фронте ряд = 8 долей (narrow=1, standard=2, wide=4). Ровно заполняют ряд
      только комбинации с суммой 8 (см. polki.html#width); иначе в ряду остаются
      пустые слоты (напр. 2 narrow + 1 wide = 6 долей).
  starts_at, ends_at
  status ENUM(active | expired | cancelled | pending_payment)
  dynamic_rank_score DECIMAL — для сортировки внутри зоны (пересчёт по правилам)
  owner_user_id — продавец (денормализация для запросов)

Product
  id, seller_id, title, ...

Payment / Order для аренды
  — Привязка к ShelfListing или отдельная сущность Transaction.

-------------------------------------------------------------------------------
5. API (ЛОГИЧЕСКИЕ ЗОНЫ, БЕЗ ПРИВЯЗКИ К СТЕКУ)
-------------------------------------------------------------------------------
5.1. Публичное API витрины
  GET /rooms/{slug} — комната с карточками, сгруппированными по зонам полки,
    только active listings.
  — Фильтрация: ends_at > now(), status = active.

5.2. Кабинет продавца
  GET /seller/listings — свои полки (активные и истёкшие).
  POST /seller/listings — создать заявку на размещение (или оплату).
  PATCH /seller/listings/{id}/renew — продление.

5.3. Админ
  GET /admin/listings — все записи с фильтрами.
  PATCH /admin/listings/{id} — принудительное изменение статуса.

5.4. Фоновые задачи
  Job every minute (или чаще): находить listings с ends_at <= now(),
    переводить в expired, скрывать из публичной выдачи.
  Job рассылки «за 24 часа»: найти listings с ends_at в окне (now+24h ± window),
    отправить письмо если ещё не отправляли (флаг last_reminder_at).

-------------------------------------------------------------------------------
6. ПИСЬМА (EMAIL)
-------------------------------------------------------------------------------
6.1. Шаблон «Заканчивается аренда полки (24ч)»
  Переменные: имя, название комнаты, название товара, дата окончания,
  ссылка «Продлить», ссылка в кабинет.

6.2. Провайдер
  — Любой SMTP / SendGrid / Mailgun / Unisender и т.д.
  — Секреты только в env, не в репозитории.

-------------------------------------------------------------------------------
7. БЕЗОПАСНОСТЬ
-------------------------------------------------------------------------------
  — Продавец видит только свои listings и свои товары.
  — Админ — по роли из JWT / сессии.
  — Rate limiting на оплату и создание listings.

-------------------------------------------------------------------------------
8. СВЯЗЬ С ТЕКУЩИМ СТАТИЧЕСКИМ ФРОНТОМ
-------------------------------------------------------------------------------
  Статические HTML заменяются или дополняются SPA/SSR, который запрашивает
  данные из API. Зоны «верх / середина / низ» на фронте соответствуют полю
  tier; бейджи ширины — width_tier; таймеры и скрытие — только после бэкенда.
